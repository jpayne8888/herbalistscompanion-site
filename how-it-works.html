How Herbalist's Companion works

Herbalist's Companion

Updated November 21, 2026

Herbalist's Companion is an herb guide and a bench for building herbal formulas, for Android, iPhone, and iPad. The guide holds fifty herbs, each with its traditional uses, energetics, tastes, actions, and cautions. On the bench, herbs are placed in four roles (Lead, Support, Synergizer, and Driver), and the app reads the blend as it grows. This page says how it is built and how shared formulas are kept safe, with engineering notes after the overview.

What it is made of

The app is written in React Native, which builds one app that runs natively on both Android and iOS, with Expo, a set of tools for building, signing, and updating React Native apps. Supabase, a hosted service built on the Postgres database, holds the accounts and the saved formulas.

The herb guide is kept on the phone once it has loaded, so it can be read without a connection. The reading of a formula (its warmth and moisture, its flavor, the actions it covers, and the cautions its herbs carry) is worked out on the phone as each herb goes onto the bench. A formula stays on the phone until it is saved, and saving needs an account. A saved formula can be read or changed only by its own account, unless its maker publishes it. The app contains no advertising, analytics, or crash-reporting SDKs.

How sharing is kept safe

Nothing is published until its maker taps Publish, and publishing needs an account. Before a first share, the app shows the rules for shared formulas and asks for agreement to the terms of use. A shared photo is hidden from everyone else until it passes an automatic check, first on the phone and then on the server. A refused photo is not kept. Any signed-in reader can report a formula, and a person reads every report. Any reader can hide a formula or its maker. An account can be deleted from Settings, and everything saved to it goes with it. The privacy policy says in full what is collected and why.

Engineering notes

The stack

The client is React Native 0.85 and React 19 on Expo SDK 56, in TypeScript with strict checking on. Screens are files under Expo Router. Data from the server is fetched and cached with TanStack Query, and every query key is defined in one module, so a write can find each cached copy it has made stale. State that belongs to the phone (the formula in progress, the theme, the text size) is held in small Zustand stores. The server is Supabase: Postgres with row-level security, sign-in over PKCE, file storage, and server functions written for Deno.

The code is layered so that the part most worth testing is the easiest to test. domain/ holds the calculations as pure functions, with no network, no storage, and no React in them. db/ holds every query, the cache, and the offline copy. store/ holds the phone's own state. Screens and components call into those three.

Specified before it is built

The app is built spec first. A piece of work with real size or risk begins as a numbered directory under specs/, and no code is written until the spec says what will be true when the work is done. There are 64 so far. One ledger lists each spec's number, its state, and what remains of it.

spec.md
What will be true, as numbered requirements (FR-067-03), with the edge cases and the decisions that belong to the owner. Each decision is recorded with its date once it is made.
plan.md
How it will be built: the layers touched, the database changes, and the order in which the parts are released.
tasks.md
The work cut into steps, each small enough to finish, check, and commit on its own.

Work is sorted by risk, and a small fix takes no spec at all, only a line in the record of what shipped. A spec states its own tier. A full spec carries all three files, and a light one carries the first alone. In both, every requirement has an acceptance entry: a line that says what is done, and what is seen, when the requirement holds.

A check enforces that shape on every new spec, and confirms that each spec has a row in the ledger with a state from a fixed list. The 63 specs written before the check existed are registered with what each one lacks, and that register can only shrink.

A spec is kept true after the work lands. When building shows that a spec was wrong or incomplete, the spec is corrected in the same commit as the code. Every change a reader will receive is entered in the release plan before work on it starts, with the version it ships in.

Standing rules have numbers

What stays true across every piece of work is kept apart from the specs, in standing documents for the product, the architecture, and the calculations. Each rule there is a numbered statement. ARC-019 says a store build comes from a release branch and never from the main line. ARC-011 says the app can write feedback and can never read it back. Code comments and tests cite the number, so the reason behind a line of code can be looked up. When a spec changes something a standing document describes, that document changes in the same commit. Above both sits a constitution of five principles that no spec may contradict.

A rule a script can check is checked by a script

A rule that rests on memory gets skipped, so a rule that can be tested is turned into a check. About sixty check scripts stand beside the test suites, and each is narrow. One fails when a code comment names a file or a function that no longer exists. One fails when a script has rewritten a data file in the wrong text encoding. One hashes every piece of text a person has approved for readers and fails when any of it changes without a recorded edit. One searches the standing documents for names that have been retired.

A check that finds old faults on its first run records them in a register that can only shrink. Anything new fails, and an entry that no longer applies is reported so it can be struck. When a fault is closed, the record says where its lesson now lives: a test, a check, a written rule, or nowhere, because it was a one-off.

The type checker runs after every edit to a TypeScript file. The herb data is typed as well, so a malformed entry does not compile. Continuous integration runs a dependency audit, the type checker, the unit and component suites, and the checks on each push to the staging branch.

The main line and the release branches are guarded on the developer's machine. One command reads the list of steps out of the integration workflow file and runs them, 34 steps in about five minutes, and a tracked pre-push hook runs that command and refuses the push if any step fails. There is one list of steps, so the two cannot drift apart.

One database, many builds

Every change to the database is a numbered SQL migration, about seventy so far, and an access rule is written in the same file as the table it guards. One production database serves every build still on a phone, so a migration written for the next version must leave the shipped one working. New columns, views, and policies are added freely. A column is dropped, or the shape of a result changed, only when no live build still reads the old one. A feature that needs the server ships switched off behind a flag held on the server, and is switched on once the builds in the field can use it.

The rules live in the database

Who may read or write a saved formula is decided by rules in the database itself, not by the app. Anything can send a request to the server, so a check made only in the app would hold only for the app. With the rules in the database, a saved formula is readable and writable by its own account and no other, whatever sends the request. They are tested the way an attacker would meet them: a suite starts a real local copy of the database, signs in as two accounts and as a visitor with none, and tries what each should and should not be able to do.

Shared photos are hidden until they pass

A photo on a shared formula is invisible to everyone but its maker until it has passed its check. Showing a photo at once and removing it later would leave a window in which anyone could see it. The check runs in two places. On the phone, the face detection built into the phone's own operating system looks for a face, and the photo is not sent anywhere for that. On the server, the photo goes to Google Cloud Vision, a Google service that reads images, which checks it for explicit content and for a human face. The face check does not recognize anyone, and nothing about a face is kept.

The check fails closed. A photo the phone cannot check is not added, and a photo the server has not passed stays hidden. The server checks every waiting photo on its own, so an app that never asks for a check still cannot make a photo visible.

The phone does the arithmetic

The formula reading is computed on the phone, in plain functions with no network in them. The bench answers as each herb lands, with no wait for a server, and a formula in progress is never sent anywhere. The herb guide is stored on the phone after its first load and read from there when there is no connection.

Signed updates

The app is built to take small fixes between store releases as updates. Each build carries a certificate and refuses any update its matching private key did not sign, and that key is kept outside the code. An update server that was taken over, or a network that tampered with the download, could not get the app to run code that key did not sign.

No third-party SDKs for ads, analytics, or crashes

The app does no analytics or usage tracking. That costs the usual instruments: there is no dashboard of what readers tap and no automatic crash report. Faults are found by tests and by what people send through the feedback form. In return, the privacy policy can name every service the app talks to, and the list is short.

Release discipline

Store builds come from a release branch cut from the main line of work, and that branch takes only fixes to what it ships. Before an Android build may be uploaded to the store, a script opens it and checks the file itself rather than the settings that produced it. It confirms that the build runs on real phones and not only the emulator, carries the right version and the release signature, was built from the current code, accepts only signed updates, asks for no hardware it does not need, and finds every database change it expects already on the server.

Tests

There are three layers. About 1,600 tests cover the pure logic. About 800 render interface components and check what they draw and do. About 300 more, in twenty suites, run against a live local database and exercise its rules as real signed-in users. A requirement of a finished spec is tied to its test by number. The test names the requirement, so a failure points back to the sentence it enforces, and a check fails when a requirement is named by no test and is not on its register. A new test is expected to fail first: the code it guards is broken on purpose, the test is seen to go red, and the code is put back. A test that passes either way guards nothing.

The interface

Every icon in the app, from the tab marks to the traditional symbols, is drawn as vector paths. Symbol characters and emoji render differently from one phone's fonts to the next, and some render as an empty box. The paper the app appears to be printed on is one image laid full screen behind everything, and its texture is held to a share of the contrast between the page and a card, so it never reads as a card. Botanical plates on the herb pages are shown whole, since a crop removes the root and the flowering head a plate is drawn to show. Type follows the reader's chosen size through four steps. No meaning rests on color alone: wherever color says something, a word or a position says it too, so the app reads the same to a color-deficient eye.

What was wrong, and what replaced it

  • The paper ground was first a small texture repeated across the screen. In all three versions tried, any mark in the texture became a pattern at a fixed spacing. One image the size of the screen has nothing to repeat.
  • The server checked shared photos only after Publish, so an unsuitable photo sat in the editor looking accepted until the end. The check now runs the moment a photo is chosen, without holding up the screen, and a photo that passes then is not sent to be checked again after upload.
  • An early Android build held native code for the emulator only. It would have installed on no real phone, and every check that day ran on an emulator, where it worked. The release script came from that.
  • Requirements were numbered and tests were written, and nothing joined the two. The first run of the trace check found 31 of 330 finished requirements named by a test. The other 299 went on a register, and a requirement comes off it when a test names it.
